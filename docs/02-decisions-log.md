# 決定事項ログ

決めたことと、まだ決めていないことを記録していく。

## 決定事項

| 項目 | 決定内容 | 理由 |
|---|---|---|
| アプリ名 | Word Learner | 本人の希望 |
| アプリの位置づけ | ハッカソン提出物。「寿司打」のゲームメカニクス(制限時間・コンボ・タイムボーナス)を引き継ぎつつ、お題は「ひらがな→ローマ字」ではなく「日本語の意味→英単語のスペル」にした英単語学習アプリとして公開する | 本人の希望。「自分で単語帳を作る画面」はコストが高いため見送り、まず英単語学習アプリとして出す |
| 単語帳作成のUI | 作らない。画面上で単語セットを作成・保存・共有する「タイピングメーカー」的な機能は持たない([01-overview.md](./01-overview.md)の「やらないこと」) | 本人の判断。ノーコードの作成UIはDB設計・保存・共有機能が必要になりスコープが大きい。git clone + AIエージェントでの書き換えの方が低コスト |
| お題データの型 | `{ meaning: string; word: string }`(日本語の意味→英単語のスペル) | 英単語学習アプリの仕様に合わせた型。フィールド名は意味的に汎用なので、他言語・他テーマへの入れ替えにも使い回せる |
| 級(難易度)分け | 英検5級/4級/3級のように問題セットを級ごとに分ける。`lib/words/grade{1,2,3}.ts`のように級単位でファイルを分けるハードコーディングで実現し、管理画面は作らない | 本人の希望。「自分で単語帳を作る画面は面倒」だが級分けはやりたい、という要望への対応 |
| 級ごとのランキング分割 | ランキングは級ごとに分ける。`game_sessions`に`grade`カラムを追加し、`grade`で絞り込んで集計する(具体的な取得方法はInertia化に伴い変更。下記[ランキングの取得方法](#決定事項)参照) | 本人の希望。級によって難易度が全然違うため、同じランキングに混ぜると公平な比較にならない |
| 級の一覧をどこで管理するか | バックエンド(DB CHECK制約・FormRequestのバリデーション)では級の一覧を持たない。`grade`は形式だけ検証する単なる文字列として扱い、「どの級が存在するか」はfrontendの`lib/words/`だけが知っている状態にする | 本人の希望(「みんなが分かりやすく使えた方がいい」)。級を増減するときにバックエンドのマイグレーション・バリデーション変更が要らず、frontendの`words`ファイルを編集するだけで済むようにするため |
| マイページ・プレイ履歴機能 | 作らない。`/mypage`画面・`GET /api/me/game-sessions`エンドポイントは持たない | 本人の判断。「クイズではなくタイピングゲームなので、履歴より(すでにある)トップページのランキングで十分」。履歴を無くしても`game_sessions`テーブル自体はランキング保存に必要なため、DB側の制約・複雑さは変わらない(削れるのは画面とAPIエンドポイントのみ) |
| ゲストプレイ | `/play`はログイン不要にする。誰でもゲームを遊べる。ログインが必要なのは**スコアをランキングに保存するとき**だけ(未ログインでプレイした場合はランキングに載らない)。これに伴い`/play`を保護するCookieガード(`proxy.ts`)は不要になる(ログイン必須ページが0個になるため) | 本人の希望。「ログインしなくても問題を解けるようにしたい」。ランキングに載らないことは本人も承知の上でのトレードオフ |
| アカウント設定機能 | 名前変更・パスワード変更・退会機能は作らない(登録時のまま変更不可) | 本人の希望。アカウント管理のスコープを増やさずシンプルに保つ |
| ログインのレートリミット | name+IPの組み合わせで1分あたり5回まで(Breeze標準の`LoginRequest`の仕組みをそのまま利用)。登録には`throttle:6,1`をかける([backend/auth.md](./backend/auth.md#ログインのレートリミット)) | 本人の希望。総当たり攻撃対策。Breezeに既に実装済みの仕組みがあったため、それをそのまま採用した |
| ログイン維持期間 | `SESSION_LIFETIME=10080`(7日) | 本人の希望。Inertia化に伴いLaravel標準のセッション設定に戻した |
| ゲームルール | 制限時間60秒固定、難易度なし。スコア=解いた問題数 | 本人の希望。シンプルに保つ |
| タイムボーナス | ノーミスで5問連続正解するごとに残り時間+1秒 | 本人の希望(デフォルト提案3問→5問に変更) |
| 技術スタック | **Laravel + Inertia.js + React**のモノリス構成(TypeScript + Tailwind CSS)。別オリジンのNext.jsフロントは廃止 | 本人の気づき。Next.jsの分離フロントとして使うはずだったSSR/ISR/SEOを実際には一切使わない設計になっていたため、「Next.jsを使う旨みが無い」と判断。同じLaravel+React構成ならInertiaの方が技術選定の理由が通る([検討した上で見送った選択肢](#検討した上で見送った選択肢)参照) |
| 構成 | Laravelが画面描画(Inertia経由でReactページを返す)とAPI的な書き込み処理の両方を担う単一アプリ。BFFという概念自体が無くなる(フロント/バックエンドが別オリジンではないため) | Inertiaへの切り替えに伴う帰結。別オリジン間の通信を前提にした設計(CORS・トークン受け渡し等)が丸ごと不要になる |
| 認証方式 | Laravel標準の**セッション認証(web guard)+CSRF**。Sanctum(トークン認証)は使わない | Inertiaは同一オリジンで動くため、Bearerトークンでドメイン間の制約を回避する理由が無くなった。Laravel Breezeの Inertia+React構成を土台にする想定([backend/auth.md](./backend/auth.md)) |
| ログイン状態の取得方法 | `HandleInertiaRequests::share()`で`auth.user`を全ページのpropsとして共有する。クライアント側で`/api/me`のようなfetchを別途行う必要はない | Inertiaの標準的なやり方。別APIを叩かなくてもページコンポーネントが`props.auth.user`をそのまま参照できる |
| ローカル開発環境 | Docker Compose([infra/local-dev.md](./infra/local-dev.md)) | 本人の希望。別プロジェクト(EC3)と同方式に揃える |
| リポジトリ構成 | 単一のLaravelアプリ(`resources/js/`配下にInertiaのReactページ)。`backend/` `frontend/`のモノレポ分割は廃止 | Inertiaはフロント・バックエンドを分けないフレームワークのため、分割する理由が無くなった |
| DB設計 | `users` / `game_sessions`の2テーブルのみ([backend/database-schema.md](./backend/database-schema.md)) | お題はDB化せず、ランキングは集計クエリで作れるため最小構成にできる |
| 認証実装の土台 | Laravel Breezeの**Inertia + React**スターターキットを土台にし、メール認証・パスワードリセット関連は削除して使う | 認証画面・ミドルウェア・コントローラを毎回手で書くより、公式スターターキットから必要な部分だけ残す方が早い。Breezeは今回使わない機能(メール認証等)も含むため、該当部分は実装時に削除する([backend/auth.md](./backend/auth.md)) |
| ランキングの取得方法 | 専用のJSON API(`GET /api/ranking`)は持たない。トップページのInertiaページが`grade`をpropとして受け取りランキングを計算して渡す。級選択を変えたら`router.reload({ only: [...] })`のpartial reloadで該当propだけ再取得する | Inertiaの標準的なデータの持たせ方。別途fetchする理由が無い([frontend/routing.md](./frontend/routing.md)) |
| お題データ | DBに持たず、`resources/js/`側に静的ファイルで保持。本人がコードを編集してデプロイする運用(管理画面は作らない) | 管理機能(CMS)が不要な機能のため、テーブルを増やす理由がない |
| お題データのファイル構成 | 単一ファイルではなく`resources/js/lib/words/`配下にカテゴリ別ファイル+`index.ts`で集約する構成 | 本人の懸念(データが増えたときの見通し)への対応。単語追加はカテゴリファイルへの1行追記で済む |
| カスタマイズ性 | 「cloneしてお題の単語セットを自分の学びたい内容に入れ替えられるテンプレート」として設計する(配色・デザインの変更は目的外)。改造は**本人が手で書くのではなく、各自のAIエージェントに指示して編集させる**ことを想定する。改造しやすさのために`// CUSTOMIZE:`コメント規約を徹底し、リポジトリルートに`AGENTS.md`を置いて[customization.md](./customization.md)を指す | 本人の希望。「手書きでカスタマイズする人はほぼいない、各自のAIに読ませて単語セットを入れ替えさせるのが現実的」という判断 |
| ランキング実装 | 専用テーブルを持たず、`game_sessions`を`grade`で絞ってスコア順に並べるだけ。自己ベストへの絞り込みはしないため、同じユーザーが上位10件に複数回登場しうる | テーブルを増やさずに実現できる。本人の希望。「個人用で繰り返し遊ぶときに自己ベストしか残らないと不便」という理由で、ユーザーごとの絞り込みをやめた |
| `played_at`カラム | 持たない。Laravel標準の`created_at`をプレイ日時として使う | 役割が重複するカラムを増やさない |
| ドキュメント構成 | `01-04`の連番4ファイル + `backend/` `frontend/` `infra/`サブディレクトリでトピック別詳細。Inertia化後も`backend/`はLaravel側(ルーティング・コントローラ・DB)、`frontend/`はInertiaのReactページ側、という**トピックの分け方**として維持する(コードのリポジトリ構成とは別の話) | 別プロジェクト(EC3)のドキュメント構成を踏襲。1アプリになってもトピック単位で見通しよく保てる |
| ランキングの画面配置 | 専用の`/ranking`ページを持たず、トップページ(`/`)のサイドバーに表示する | 本人の希望。わざわざページ遷移しなくても常に見える位置に置く |
| ゲームモード | 「学習モード(答えを見ながら練習)」と「チャレンジモード(答えを隠して挑戦)」の2モードを用意する。**スコア保存・ランキング参加はチャレンジモードのみ対象**。学習モードはタイピング練習・暗記の定着用で、スコアは保存しない | 本人の希望(画面モック)。答えを見ながら打てるモードと、答えを隠して記憶力を試すモードを両立させたい。学習モードのスコアを保存すると、答えが見えている分有利なスコアがランキングに混ざり不公平になるため対象外にした |
| タイマー表示形式 | `mm:ss`形式(例: `01:24`)で表示する。単純な秒数カウンタではない | 本人の希望(画面モック)。タイムボーナスで60秒を超えて延びることがあるため |
| 問題番号表示 | ゲーム画面に「QUESTION 01」のように現在の問題番号を表示する(完了した単語数+1。スコアと連動) | 本人の希望(画面モック) |
| 級・モードの選択場所 | 級とモードの選択はトップページ(`/`)で行い、「START GAME」を押した時点で選択済みの状態のまま`/play`に遷移してすぐにゲームが始まる(`/play`内では選択UIを出さない)。トップページのランキングパネルも、同じ「SELECT LEVEL」の選択値と連動して表示する級が切り替わる(専用の`GradeTabs`は作らず、1つの選択状態をゲーム開始とランキング表示の両方で共有する) | 本人の希望(画面モック)。選択UIを一箇所にまとめ、二度選ばせない |
| 出題順 | 完全ランダムではなく、級の単語リストをシャッフルして使い切るまで繰り返さない「バッグ方式」にする([frontend/game-engine.md](./frontend/game-engine.md)) | 本人の希望。完全ランダムだと同じ単語が短い間隔で何度も出る偏りがあり、学習アプリとして体験が良くないため |
| 1問あたりの制限時間 | チャレンジモードのみ、1問7秒を超えたら自動的にミス扱いでスキップする(スコアは増やさずコンボを0にリセット)。学習モードには適用しない。残り時間の視覚的なフィードバック(プログレスバー等)は表示しない | 本人の希望。答えが分からず止まってしまう問題で時間を溶かさないようにするため。学習モードは答えが見えているので時間切れの心配が無く不要 |
| お題の単語リストの用意方法 | 実装フェーズでAIエージェントが英検5級/4級/3級それぞれの一般的な頻出単語を参考に作成する(50〜100語程度/級)。後から本人が追加・差し替え可能 | 本人の希望。自前の単語リストが無いため |
| ランキングの同点スコア順位 | `score`降順、同点の場合は`created_at`昇順(先にそのスコアに到達した方を上位にする) | 本人の希望。「先に達成した人が偉い」という自然なルール |
| `/play`への不正アクセス時の挙動 | `grade`または`mode`が欠落・不正な場合はトップページ(`/`)へリダイレクトする(デフォルト値で始めることはしない) | 本人の希望。級・モードは必ずトップページで選んでから始める、という導線を保つため |
| 期間別ランキング(DAILY/ALL TIME) | 採用しない。引き続きALL TIMEのみ | 画面モックではDAILY/ALL TIMEタブがあったが、検討の結果見送り。以前の決定([03-features.md](./03-features.md)の「あったら良い(見送り)」)を維持 |
| デプロイ先 | Railwayの**サービス1つ**にアプリ本体(Laravel+Inertia)をデプロイし、PostgreSQLプラグインを追加する。[infra/railway.md](./infra/railway.md) | 単一アプリになったため、分けるべきfrontend/backendという区分自体が無い。ISRや高度なキャッシュ戦略が必要な要件も無い |
| 本番ドメイン構成 | 考慮不要。単一アプリ・単一オリジンなので、CORSやCookie/セッションのドメイン共有を気にする必要がそもそも無い | Inertia化によってfrontend/backendが別オリジンという前提が無くなったため、この論点自体が消滅した(旧: Bearerトークン認証を選んだ理由がこの制約の回避だった) |

## 未決定(これから詰める項目)

- お題の単語リストの具体的な内容・収録数(50〜100語程度を想定しているが、実際の選定は実装時に行う)

## 検討した上で見送った選択肢

| 項目 | 検討した選択肢 | 見送った理由 |
|---|---|---|
| 構成 | Laravelモノリス(Blade+Livewire) | Next.jsを使い続けたい本人の希望により分離構成を選択(後にInertia+Reactのモノリスへ再度方向転換、下記参照) |
| 認証方式(2周目の初期案、後に撤回) | Sanctumのセッション認証(SPA認証、Cookie+CSRF) | 当初はローカルが`localhost:3000`/`8000`構成になり追加設定なしでCookie共有できることを理由に採用したが、本番でRailwayの無料ドメインのまま運用するとカスタムドメインが必須になることが判明し、Bearerトークン認証に変更した(その後Inertia化でこの論点自体が不要に) |
| バックエンド | フロントエンド単独(Next.js API Routes+Prisma) | 最初の案だったが、本人がLaravelを使いたいとの希望で変更 |
| 構成(2周目、後に撤回) | Laravel(API専用)+Next.js(App Router)の分離構成、Sanctumパーソナルアクセストークン(Bearer)認証、Railway2サービス(frontend/backend別々)デプロイ | EC3(別プロジェクト)と揃えるために採用し、一通りdocsを作り込んだ。しかしNext.jsを使う決め手だったSSR/ISR/SEOを実際には一切使っておらず(BFF不採用・全ページクライアントコンポーネント中心・Railwayに一本化してISR不要と判断済み)、「Next.jsを分離フロントとして使う理由が無い」と本人が気づいたため、Laravel + Inertia.js + Reactのモノリス構成に切り替えた。Bearerトークン認証・Railway2サービス・frontend/backend分離の各決定もこの切り替えに伴いまとめて撤回 |
